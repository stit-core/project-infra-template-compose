# Skill: plan

Долгосрочный планировщик. Применяется когда задача больше «правка одного файла»
и её надо разложить на атомы, закрыть открытые вопросы, и только потом работать.

`.claude/plans/roadmap.md` — индекс активных задач. `.claude/plans/<slug>.md` —
детальный план одной задачи. Оба committable, ревьюятся, forward-only.

## Когда применять

- «Распиши план для X» / «сначала запланируем» / «/plan <задача>»
- Задача меняет топологию (>2 сервиса / networking), `configs/vault-agent/`
  (`agent.hcl.parts/`, `templates/`), traefik static, backup-стратегию
- Многошаговая миграция KV-layout / env-контракта / ansible-роли
- Юзер не уверен в требованиях — план превращает разговор в письменный артефакт

## Когда НЕ применять

- Атомарная задача (один Edit, одна `${VAR}`, опечатка) — план дороже работы
- **«Сломалось» / deploy упал / сервис unhealthy / cert не выписался → skill
  `triage`** (петля RED→GREEN), НЕ `plan`. Исключение — research-spike, когда
  корневая причина неясна после ≥2 попыток (план именно на spike).
- Юзер дал готовый список шагов — записать в `<slug>.md` без декомпозиции

## Жизненный цикл

```
PLANNING     — собираем контекст, задаём вопросы, пишем атомы
  ↓ (юзер approve)
IN-PROGRESS  — выполняем атомы, помечаем done с evidence (коммит-хеш / make-верб)
  ↓
CHECKPOINT   — на границе фазы / 3+ атома / новый вопрос: сверка с реальностью
  ↓
DONE         — все атомы зелёные, slug.md удаляется сразу (история в git log)
```

## Шаги

### 1. Понять задачу до записи плана

Спрашивай **до** плана. План на догадках хуже разговора. Минимум 3-5 релевантных:

**Скоуп** — что входит / что НЕ входит? фича / рефактор / миграция? связано с другим PR?

**Env / секреты** — новый `${VAR}` в compose/configs? Он identity (.env) или
Vault-managed (`kv/projects/<p>/<env>/*`)? Нужен новый KV-объект → seed корп-стороной?

**Топология / networking** — новый сервис? в какой сети (`proxy` / `backend-net`)?
публичный (traefik + `crowdsec@file`)? зависит от vault-agent / postgres? профиль?

**Vault-KV зависимости** — какой профиль (`postgres`/`storage`/`backend`/...)
включается? какие KV-paths обязаны быть засеяны до старта? `agent.hcl.parts/`
правится?

**Rollout / downtime** — рестарт traefik static = downtime? force-recreate
consumer'ов (смена `env_file`)? порядок выкатки (vault-agent first)?

**Откат** — что если деплой красный на проде? down-путь реально откатывает?
backup/restore-point на месте до destructive-шага?

Если на 5+ вопросов «не знаю / решай сам» — задача недозрелая. Предложи отложить
или сначала research-spike.

### 2. Сгенерировать slug

`<verb>-<object>[-<qualifier>]`, kebab-case, 2-4 слова, без даты:
`add-pyroscope-service`, `migrate-kv-layout-v2`, `split-staging-env`.
Проверь, что `.claude/plans/<slug>.md` не существует (иначе суффикс `-v2`).

### 3. Записать `.claude/plans/<slug>.md`

```markdown
# <Понятный заголовок>

**Slug:** `<slug>`
**Создан:** <YYYY-MM-DD>
**Статус:** planning
**Последний чекпоинт:** —

## Контекст

<2-5 предложений: зачем, что известно, что пробовали. Ссылки на файлы
`path:line`, коммиты, rules (`.claude/rules/multi-env.md` и т.п.).>

## Не входит в скоуп

- <что осознанно не делаем>

## Открытые вопросы

- [x] Q1: <вопрос> → <ответ юзера>
- [ ] Q2: <не закрытый — блокирует какие атомы?>

## Атомы

<Стандарт атома (валидируется `make plan-check`):
 - Ровно 1 коммит-worth (cohesive; крупное — дроби).
 - `Verify:` ОБЯЗАТЕЛЕН — canonical make-верб + ожидаемый результат
   (`make check` зелёный / `make ps` healthy / `make doctor` OK).
 - `Зависит от:` явно (атом/slug или —).
 - По закрытии — строка `**Done:**` с evidence (коммит-хеш / `make check → OK`).
 Лимит ~15. Большой план — фазы `### Phase N — <name>` + чекпоинт на границе.
 >15 атомов — задача слишком крупная: 2+ зависимых плана (`(after <slug>)`).>

### Phase 1 — <name>   (фазы — для больших планов; мелкий — без фаз)

- [ ] **A1:** <короткое описание>
  - Что делаем: <1-2 строки>
  - Файлы: `compose/x.yml`, `configs/...`
  - Verify: `make check` → OK
  - Зависит от: —

## Corp impact

<Заполняется когда атом задевает corp-поверхность (см.
`.claude/rules/corp-handoff.md`). Каждая запись — CORP-HANDOFF-айтем
(WHAT/WHY/ACTION/WHO/DECIDE/RISK). `scripts/ship.sh` агрегирует эту секцию.
План forward-only и удаляется по закрытии — айтем обязан доехать до
corp-стороны ДО закрытия (см. §8).>

—

## Чекпоинты

—
```

### 4. Зарегистрировать в `roadmap.md`

Добавь строку в `## Активные` (формат репо):

```
- [planning] [`<slug>`](./<slug>.md) — <одна строка сути>. <N> атомов, 0/N.
```

Межплановая зависимость — суффикс `(after <slug>)`: план-B не стартует, пока
`<slug>` не DONE. `## Планируется` — idea-state без атомов; промоушн в Активные =
прогон через этот skill.

### 5. Стоп. Покажи план юзеру.

Не начинай выполнение. Покажи: путь к `<slug>.md`, резюме 3-5 строк, открытые
вопросы. Спроси: «Approve и поехали? Или ещё подумать?»

### 6. Approve → IN-PROGRESS

`Статус: in-progress` в `<slug>.md`; обнови строку в roadmap (`planning` →
`in-progress`). Дальше по атомам. На каждый закрытый:
- `[ ]` → `[x]` + строка `**Done:** <evidence>` (коммит-хеш / `make check → OK`)
- Атом задел corp-поверхность → CORP-HANDOFF-айтем в `## Corp impact` (skill `corp-handoff`)
- Обнови счётчик в roadmap (`X/N`); большой план — границы фаз
- Чекпоинт-триггеры — §7; на границе фазы чекпоинт обязателен

### 7. Чекпоинты

Триггеры: закрыто 3+ атома · новый открытый вопрос · план оказался неверным ·
юзер вернулся после паузы. В `## Чекпоинты`:

```
### <YYYY-MM-DD> — <повод>
- Закрыто: A1, A2 ✓ (коммиты)
- Обнаружено: <неочевидное>
- Переоценил: <что и почему>
- Следующий шаг: A3
```

### 8. DONE

1. **`## Corp impact` не пуст и не сдан?** Айтемы обязаны доехать до corp-стороны:
   либо `make ship` их сагрегировал и юзер передал корп-админу, либо перенеси
   строкой в `roadmap.md ## Активные` как follow-up. Удалять план с несданным
   corp-impact нельзя.
2. Удали строку `<slug>` из `## Активные`. Разблокированные `(after <slug>)` — отметь.
3. Удали `<slug>.md` — история в `git log`. Секции «выполненных» roadmap не держит.
4. Незакрытый follow-up (вкл. несданный corp-impact) — отдельной строкой в `## Активные`.
5. Сообщи юзеру: задача закрыта, план удалён.

## Что планировщик делает дотошно

- Спрашивает до того как писать. План на догадках бесполезен.
- Атомы реально атомарные. «Поднять observability-стек» — не атом, а план в плане.
- `Verify:` (canonical make-верб) у каждого атома. `make plan-check` это валидирует.
- Зависимости явные. Межплановые — `(after <slug>)` в roadmap.
- «Не входит в скоуп» — отдельная секция, дисциплинирует.
- Атом задел corp-поверхность — `## Corp impact` сразу, не «потом».

## Что НЕ делает

- ❌ Не пишет план «из головы» пропустив вопросы.
- ❌ Не обещает >~15 атомов в одном плане — split на зависимые.
- ❌ Не правит compose/configs/scripts в фазе planning. Только roadmap.md и slug.md.
- ❌ Не решает спорные дизайн-вопросы сам. Спрашивает.
- ❌ Не игнорирует существующий in-progress план — продолжает его, не плодит параллельный.
- ❌ Не планирует багфикс. Баг / «сломалось» → `triage`.

## Восстановление после /clear

1. `make status` → секция `== Plan ==` (активные slug из roadmap).
2. Прочитай `roadmap.md` — статусы; затем `<slug>.md` — последний чекпоинт, открытые атомы.
3. Сверься с `git log` с момента чекпоинта — что реально произошло.
4. Чекпоинт-запись с расхождением, если есть. Продолжай со следующего открытого атома.

План — контракт между тобой-сейчас и тобой-через-неделю. Пиши так, чтобы продолжить с пол-оборота.
