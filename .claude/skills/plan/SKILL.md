# Skill: plan

Планировщик инфры. **Planning-first** — содержательное изменение идёт через план. План —
это inline-секция в единственном артефакте `.claude/plans/roadmap.md`: `### <slug> — <title>`
под `## Active`. Отдельных per-plan файлов, подпапок и архивов нет — один файл, чтобы
документация не расходилась с правдой.

План переживает `/clear` и перезапуск: он закоммичен, ревьюится, читается заново в начале
сессии. Пиши так, чтобы тебя-через-неделю продолжил с пол-оборота.

## Когда применять

- "/plan <задача>", "распиши план", "сначала запланируем", "давай спланируем".
- Любое **содержательное** изменение: новый сервис, рефакторинг compose/configs, миграция
  KV-layout / env-контракта / ansible-роли, правка топологии (>2 сервиса / networking),
  `configs/vault-agent/` (`agent.hcl.parts/`, `templates/`), traefik static, backup-стратегия,
  security-sensitive.
- Требования размыты — план превращает разговор в письменный контракт.

## Когда НЕ применять

- **Truly-atomic** правка: опечатка, один очевидный файл, одна `${VAR}`, тривиальный one-liner.
  План дороже работы. Делай напрямую (но RED→GREEN по дефолту: `make validate`/`make doctor`).
- **Багфикс — НИКОГДА не `plan`.** «Сломалось» / deploy упал / сервис unhealthy / cert не
  выписался / vault-agent залип → skill `triage` (строгая RED→GREEN петля). Исключение —
  research-spike, когда корневая причина неясна после ≥2 попыток: тогда план именно на spike.
- Юзер уже дал готовый список шагов — запиши секцию без переспрашивания, но всё равно
  атомизируй и добавь Verify.

## Жизненный цикл

```
planning      — собираем контекст, задаём вопросы, пишем атомы
  ↓ approve
in-progress   — выполняем атомы, помечаем [x] + **Done:** evidence
  ↺ blocked   — упёрлись во внешнее/вопрос: Статус: blocked (blocked by: ...)
  ↓ все атомы зелёные
done          — ### -секция удаляется из roadmap (история в git log)
```

## Шаги

### 1. Понять задачу до записи плана

Спрашивай **до** записи — план на догадках хуже разговора. Дизайн-вопросы не решай сам —
спрашивай через `AskUserQuestion`. Минимум 3–5 релевантных под задачу:

- **Скоуп** — что входит / что осознанно НЕ входит? фича / рефактор / миграция?
- **Env / секреты** — новый `${VAR}`? Он identity (`.env`) или Vault-managed
  (`kv/projects/<p>/<env>/*`)? Нужен новый KV-объект → seed корп-стороной (skill `request-secret`)?
- **Топология / networking** — новый сервис? сеть (`proxy` / `backend-net`)? публичный
  (traefik + `crowdsec@file`)? зависит от vault-agent / postgres? какой профиль?
- **Vault-KV зависимости** — какой профиль (`postgres`/`storage`/`backend`/…) включается?
  какие KV-paths обязаны быть засеяны до старта? правится ли `agent.hcl.parts/`?
- **Rollout / downtime** — рестарт traefik static = downtime? force-recreate consumer'ов
  (смена `env_file`)? порядок выкатки (vault-agent first)?
- **Откат** — деплой красный на проде — down-путь реально откатывает? backup/restore-point
  на месте до destructive-шага?

Если на 5+ вопросов «не знаю / решай сам» — задача недозрелая: предложи research-spike или отложить.

### 2. Slug

`<verb>-<object>[-<qualifier>]`, kebab-case, 2–4 слова, без даты: `add-pyroscope-service`,
`migrate-kv-layout-v2`, `split-staging-env`. Проверь, что секции `### <slug>` ещё нет в
roadmap; коллизия → суффикс `-v2`.

### 3. Записать inline-секцию в `.claude/plans/roadmap.md` (под `## Active`)

Шаблон ниже. Подсекции — **bold-лейблы** (не `##`/`###`, они зарезервированы за план-секцией),
фазы — `####`.

```markdown
### <slug> — <понятный заголовок>
**Создан:** <YYYY-MM-DD> · **Статус:** planning

**Контекст.** <2–5 предложений: зачем, что известно, что пробовали; ссылки file:line, коммиты, rules.>

**Не входит в скоуп.** <что осознанно не делаем — дисциплинирует.>

**Открытые вопросы.**
- [x] Q1: <вопрос> → <ответ>
- [ ] Q2: <не закрыт — блокирует какие атомы?>

**Атомы.**

#### Phase 1 — <name>   (фазы — только для больших планов; мелкий — плоский список)
- [ ] **A1:** <короткое описание; ~1 коммит, ≤1 файл в среднем>
  - Verify: `make validate` → OK · Зависит от: —
- [ ] **A2:** <…>
  - Verify: `make check` → green · Зависит от: A1

**Corp impact.** — | <CORP-HANDOFF-айтемы WHAT/WHY/ACTION/WHO/DECIDE/RISK; см. skill corp-handoff>

**Чекпоинты.**
- —
```

Стандарт атома (валидируется `scripts/tools/validate-plan.sh`):
- Ровно 1 коммит-worth работы; крупное — дроби.
- `Verify:` ОБЯЗАТЕЛЕН — конкретная `make`-команда + ожидаемый результат
  (`make check` зелёный / `make ps` healthy / `make doctor` OK / `make plan-check` OK).
- `Зависит от:` ОБЯЗАТЕЛЕН (атом `A<N>` этой секции или `—`).
- По закрытии — под-буллет `- **Done:** <evidence>` (коммит-хеш / `make check → OK`).
- Лимит ~15 атомов на план. Больше — разбей на 2+ зависимых плана (вторая `### `-секция с
  пометкой `(after <slug>)` в заголовке/контексте). Один сквозной gold-standard-план —
  осознанное исключение, проговаривается.

### 4. Стоп. Покажи план юзеру

Не начинай выполнение. Покажи: краткое резюме (3–5 строк), открытые вопросы, спроси
«Approve и поехали? Или ещё подумать?». Юзер: approve / поправить / встречный вопрос / отложить.

### 5. Approve → in-progress

`**Статус:** planning` → `in-progress`. Обнови `**Current focus:**` в шапке roadmap.
Дальше иди по атомам:
- `[ ]` → `[x]` + под-буллет `- **Done:** <evidence>` (что сделано/обнаружено).
- Атом задел corp-поверхность → айтем в `**Corp impact.**` (skill `corp-handoff`).
  `scripts/ship.sh` агрегирует эту подсекцию — айтем доедет до корп-стороны.
- На границе фазы / каждые 3+ атома — чекпоинт (§6).

### 6. Чекпоинты

Триггеры: закрыто 3+ атома, новый открытый вопрос, план оказался неверным, юзер вернулся
после паузы. Запись — **буллет** под `**Чекпоинты.**` (НЕ `### ` — это план-секция):

```markdown
- **<YYYY-MM-DD> · <короткий заголовок>.**
  - Закрыто: A1, A2, A3 ✓
  - Обнаружено: <неочевидное>
  - Переоценил: A5 теперь блокирован Q3 → новый вопрос в Открытых
  - Следующий шаг: A4
```

### 7. Blocked

Упёрлись во внешнее (корп-seed, чужой PR, решение юзера, недоступный ресурс) → `**Статус:**
blocked (blocked by: <что>)`. Blocked без пометки `blocked by` валидатор отвергает.
Разблокировалось → вернуть `in-progress` + чекпоинт-запись.

### 8. DONE

Когда все атомы `[x]`:
1. **`**Corp impact.**` не пуст и не сдан?** Айтемы обязаны доехать до корп-стороны: либо
   `make ship` их сагрегировал и юзер передал корп-админу, либо перенеси строкой в
   `## Backlog` / новую `### `-секцию. Удалять план с несданным corp-impact нельзя.
2. Удали `### <slug>`-секцию целиком из `## Active`. История — в `git log`.
3. Разблокирован зависевший `(after <slug>)` план — отметь.
4. Незакрытый follow-up — отдельной строкой в `## Backlog` или новой `### `-секцией, не
   хвостом в удаляемой.
5. Обнови `**Current focus:**`. Сообщи юзеру: закрыто, секция удалена.

## Восстановление после /clear

1. Прочитай `.claude/plans/roadmap.md` — `**Current focus:**`, секции в `## Active`, их статусы
   (`make status` → `== Plan ==` показывает slug + статус + следующий открытый атом).
2. В активной секции — последний чекпоинт, незакрытые атомы.
3. Сверься с `git log` с момента последнего чекпоинта — что план не отразил.
4. Расхождение → чекпоинт-запись. Продолжай со следующего открытого атома. Не перепланируй
   существующий in-progress план и не создавай параллельный.

## Что делает дотошно

- Спрашивает до записи; дизайн-решения — через `AskUserQuestion`, не угадывает.
- Атомы реально атомарны: «поднять observability-стек» — это план, не атом. Дроби.
- У каждого атома Verify (`make`-верб) и явная зависимость.
- «Не входит в скоуп» — отдельной подсекцией.
- Corp-impact заполняется сразу, не «потом» (доедет до корп-стороны через `make ship`).
- `scripts/tools/validate-plan.sh` зелёный перед коммитом roadmap (gate — `make check` + pre-commit).

## Что НЕ делает

- ❌ Не пишет план без вопросов.
- ❌ Не правит compose/configs/scripts в фазе planning — только `roadmap.md`.
- ❌ Не заводит отдельные per-plan файлы, подпапки, done/-архив — единый roadmap.
- ❌ Не использует `### `/`## ` внутри плана для подсекций/чекпоинтов (коллизия с план-секцией) —
  bold-лейблы и `#### ` для фаз.
- ❌ Не ведёт багфикс — это `triage`.
- ❌ Не игнорирует активный план — продолжает его, не плодит параллельный.
